### 技术澄清（已告知用户）
- Windows 的 Z 序带（Z-Band）机制：普通进程**无法**让 Taskmgr 稳定压在自己的 `HWND_TOPMOST` 窗口之上（Taskmgr 属更高 Z-band / UIAccess）。只能靠"我方主动让位"实现。
- 同层内 `SetWindowPos(hwnd, hwndTaskmgr, ...)` 可精确插到 Taskmgr 之下，但跨 Z-band 时会被系统拒绝，需回退到"临时隐藏覆盖层"。

### 踩坑记录（重要，后续维护必看）
1. **MinGW 下 `<gdiplus.h>` 必须在之前包含 `<objidl.h>`**，否则 `PROPID` 未定义导致大量编译错误（WIN32_LEAN_AND_MEAN 会裁掉它）。
2. **`--startup` 参数必须用 `GetCommandLineW()` 解析**，不要依赖 `wWinMain` 的 `lpCmdLine`（MinGW `-municode` 下不可靠）。
3. ⚠️ **Windows 会在前台窗口完整性级别变化时自动清除 `ClipCursor`**：打开任务管理器（提权/高 IL）后 clipRect 被重置为全屏，关闭时再清一次。已实现 `ReassertClip()` 在 500ms 巡检里周期性重新裁剪（验证：高 IL 前台下重新裁剪仍然有效）。副作用：提权窗口前台期间低 IL 进程既不能挂钩也不能裁剪 → 锁定暂时失效，切回普通窗口 0.5s 内自愈。这是 UIPI 安全边界，无法绕过（除非提权运行）。
4. `SetCursorPos` 目标点超出屏幕边界会直接失败（光标不动），写自动化测试时目标点必须在屏幕内，否则误判"已锁定"。
5. PowerShell 函数参数**不要命名为 `$args`**（与自动变量冲突，会导致 `-ArgumentList` 传空）。
6. Windows PowerShell 5.1 读取无 BOM 的中文 .ps1 会按 GBK 解析而报错 —— 临时测试脚本用纯 ASCII。
7. 进程被 `Stop-Process` 强杀时不会执行 `Cleanup()`，`ClipCursor` 不会释放 → 测试脚本结尾必须 `ClipCursor(NULL)` 兜底。
8. 编译产物被占用：测试前必须先 `Stop-Process mouse_lock`，否则 `ld.exe: Permission denied`。

### 迭代 4：调试模式 + 修复「每 5 秒误锁」严重 BUG（2026-08-31）
- 用户反馈「现在每5秒自动锁」并要求加调试模式开关。
- **调试模式**（配置 `Debug`，托盘菜单「调试模式」勾选）：日志写 `%APPDATA%\MouseLock\debug.log`（>2MB 重写），记录 start 配置快照、每秒 TICK（idle/阈值/锁定态/taskmgr/session/计时状态/glitch 计数）、INPUT detected（输入刷新计时）、HOTKEY（含 mods/vk）、LOCK/UNLOCK（带 reason：hotkey-ctrl-o / hotkey-ctrl-shift-o / menu-*/tray-double-click / idle-timeout / session-lock / system-suspend / session-end / startup）、IDLE-TRIGGER 原始数值；托盘提示实时显示空闲倒计时。
- **BUG 根因（竞态）**：`IdleElapsedMs()` 先取 `now=GetTickCount()`，再调 `GetLastInputInfo()`；若按键恰在两次调用之间到达，`last` 新于 `now`，`DWORD` 无符号相减绕成 ~49 天的巨大值 → 立即判定超过 5 分钟阈值 → 误锁。实测高频打字 30 秒内触发 3–11 次（间隔约 3–5 秒，与用户"每5秒"完全吻合）。
- **修复三处**：
  1. `IdleElapsedMs()` 中 `if ((int)(now - last) < 0) return 0;`（钳制，并计入 `g_dbgGlitch`）；
  2. `GetLastInputInfo()` 失败时不再回退 `g_lastMouseTick`（只打字不动鼠标时它可能是几分钟前的值），改为返回 `GetTickCount()` 视为"此刻有活动"；
  3. 超时需连续两次巡检（约 1 秒）都成立才锁定（`g_idleOverTicks`），抵御单次采样抖动。
- **验证**：25 秒高频打字 → glitch=3、误锁 0（修复前同等强度会误锁 ~11 次）；临时把阈值单位改秒的测试构建确认真实空闲超时仍会触发（5.9s 触发 5s 阈值），无回归。
- 教训：两个 `DWORD` 时间戳相减前必须判方向，Windows 上 "取 now 再取 last" 的顺序天然存在 last>now 的窗口。
- 最终配置：IdleEnabled=1 / IdleMinutes=5 / IdleMode=1 / Strict=1 / ShotEnabled=1 / SaveShot=0 / LockOnStart=0 / Debug=1（调试开着，用户用完可在托盘关掉）。临时文件 `_idletest.*` 已删除。

### 迭代 6：日志排查「吃饭回来没自动锁」+ 合成输入过滤（2026-08-31）
- 用户反馈：12:00 出门吃饭，12:18 回来发现没自动锁定。
- **日志结论（debug.log）**：程序自 11:49:15 起一直在跑（`LockOnStart=0` 所以启动不锁），11:49–12:18 期间**没有任何 LOCK 事件**；12:00–12:18 共记录 **1139 次 INPUT 事件，平均每秒 1 次，最大间隔 2 秒**，空闲值长期为 0，最大连续空闲仅 **124 秒**，永远够不到 300 秒阈值。
- **根因**：机器上装有 **AweSun（向日葵）、RustDesk、ToDesk** 三个远控软件，会定时注入输入防休眠；`GetLastInputInfo()` 把**合成输入也算作用户活动**，空闲计时被反复清零。
  - 旁证：用户回来后采样 15 秒，光标 0/60 次移动、lastInput 正常增长到 19.5 秒 → 注入只在"机器空闲一段时间后"才启动。
- **修复（两项）**：
  1. 新增 `IdleMode=2`（`kIdleRealInputOnly`）：鼠标+键盘都算活动，但用新增的 `WH_KEYBOARD_LL` 钩子与 `LLMHF_INJECTED` / `LLKHF_INJECTED` 标记**过滤合成输入**；鼠标还要求累计位移 ≥ `kMoveThresholdPx`(3) 才计入。设置界面把两个 radio 换成 `IDC_CB_IDLEMODE` 下拉框（3 项）。
  2. **移除「任务管理器存在就暂停空闲计时」**（原来 `IdleTimerActive()` 含 `!g_taskmgrPresent`，用户 12:18 开的任务管理器一直挂着，会让自动锁定彻底失效）。现在任务管理器只影响"截图层让位"，不再干扰计时——用户操作它时本身就会产生真实输入。
- **验证**：
  - IdleMode=0：注入 10 次合成移动 → 空闲 5000→11000ms 继续增长，`moves(r/i)=0/10`。
  - IdleMode=1（对照）：注入后空闲被重置回 16ms → 合成输入确实被计入。
  - IdleMode=2：注入 10 次合成鼠标 + 10 次合成按键 → 全部忽略，空闲 5015→11015ms。
  - 端到端（临时把阈值改成秒的构建）：**任务管理器开着 + 持续注入 32 次合成鼠标 + 32 次合成按键**，仍在 4.5s 触发 `IDLE-TRIGGER elapsed=4500/4000` 并 `LOCK reason=idle-timeout`。
- 调试日志新增 `moves(r/i)=真实/忽略` 与 `keys(r/i)=真实/忽略` 两列，用于判断离开后是否仍有"真实"输入（若 real 仍增长，说明是虚拟 HID 驱动级注入，无解）。
- 最终配置：IdleMinutes=5 / **IdleMode=2** / Strict=1 / ShotEnabled=1 / SaveShot=0 / LockOnStart=0 / Debug=1 / HideTray=0。临时文件 `_t2.*` 已删除，进程已清空。

### 迭代 7：设计讨论「截图置顶后是否还需锁鼠标」（2026-08-31，未编码）
- 用户提问：截图已全屏置顶，是否不必再锁鼠标？
- **分析结论**：当前组合（单屏 + C5 不穿透）下确实存在冗余——覆盖窗口吸收点击与滚轮，视觉也已冻结，再锁鼠标收益有限。
- **但锁鼠标不可省的场景（4 个）**：
  1. **多显示器**：C1=② 只截鼠标所在显示器，其它屏幕完全暴露，可自由操作。
  2. **任务管理器让位时**：截图层被隐藏（F1），屏幕完全暴露，只能靠锁鼠标兜底。
  3. **关闭截图功能时**（ShotEnabled=0），锁鼠标是唯一手段。
  4. 若将来改用「穿透」覆盖层（C5=②），点击会穿到底下程序，必须锁鼠标。
- **建议方案：新增「冻结屏幕」模式（LockMode）**
  - `LockMode=0` 锁鼠标（现状：钩子 + ClipCursor，可带或不带截图）
  - `LockMode=1` 冻结屏幕（新：截图置顶 + **不锁鼠标、不拦截移动**）
  - 冻结屏幕模式的好处：绕开 UIPI 顽疾（提权窗口前台会清除 ClipCursor、低 IL 钩子失效）；消除每 500ms `ReassertClip` 把光标拽回锚点的突兀感；解锁后光标停在原位无缝继续；不装钩子更低侵入。
  - 关键配套：
    a. **鼠标锁定的自动接管**：截图层可见 → 不锁；截图层因任何原因隐藏（任务管理器让位）→ 自动临时切回锁鼠标兜底。
    b. 不锁鼠标时截图是静态的、看不到光标 → 需在覆盖层上**实时绘制跟随鼠标的光标**。
    c. 多显示器需配合「覆盖所有显示器」选项（`ShotAllMonitors`）才敢不锁鼠标。
- 待用户拍板：① 冻结屏幕是否设为默认 ② 多屏是否全覆盖 ③ 是否绘制跟随光标 ④ 让位时兜底策略 ⑤ 进阶：是否用已有的 `WH_KEYBOARD_LL` 钩子吸收除解锁热键外的所有按键（变成真正的锁屏，键盘也不漏）。

### 迭代 8：实现「冻结屏幕」模式（2026-08-31，已完成并测试）
- **用户拍板**：① 冻结屏幕设为默认 ② 多显示器全覆盖暂缓（单屏）③ 不画跟随光标 ④ 让位时临时锁鼠标兜底 ⑤ 先不禁键盘。
- **实现要点**：
  - 新增 `LockMode` 配置（0=锁鼠标 / 1=冻结屏幕，默认 1），设置界面加 `IDC_CB_LOCKMODE` 下拉框（窗口高度 330→360，按钮下移到 300）。
  - 新增 `NeedMouseLock()`：冻结模式下，仅在**截图层没盖住屏幕**时才锁鼠标（`!g_cfg.shotEnabled || g_monitorCount > 1 || !g_coverShowing`）。
  - 新增缓存标志 `g_coverShowing`（在 ShowCover/HideCover/DestroyCover 中维护）与 `g_monitorCount`（启动时 `GetSystemMetrics(SM_CMONITORS)` 缓存一次）。**`NeedMouseLock()` 会在鼠标钩子回调里高频调用，绝不能调窗口 API，只能读缓存。**
  - `ApplyLock()` / `ReassertClip()` / 钩子拦截判断，全部改为 `g_locked && !g_menuOpen && NeedMouseLock()`。
  - 让位切换处（OnMainTimer 的 taskmgr 状态变化分支）**两侧都要补 `ApplyLock()`**：隐藏覆盖层后接管为锁鼠标，恢复覆盖层后交还冻结模式。
- **测试结果（全部符合预期）**：
  | 场景 | 截图层 | 鼠标 | 判定 |
  | --- | --- | --- | --- |
  | 冻结模式锁定 | visible | 可移动 | PASS |
  | 打开任务管理器 | hidden | 被锁住（自动接管） | PASS |
  | 关闭任务管理器 | visible | 可移动（自动交还） | PASS |
  | 锁鼠标模式锁定 | visible | 被钉住 | PASS |
  - 日志佐证：`cover hidden (yielded)` → `taskmgr=1 coverShowing=0 needMouseLock=1`。
- 顺带收益：默认模式不再依赖钩子/ClipCursor → 绕开了 UIPI（提权窗口前台清除 clip）顽疾，也消除了 500ms 重新裁剪把光标拽回锚点的突兀感。
- 托盘文案按模式区分：「屏幕已冻结」/「鼠标已锁定」。TICK 日志新增 `cover=` 与 `mouselock=` 两列。

- 遗留（用户说暂缓）：多显示器全覆盖（`ShotAllMonitors`）；键盘吸收（进阶锁屏）。

### 迭代 9：冻结模式截图不画鼠标光标（2026-08-31，已完成并验证）
- 用户提出：冻结模式锁定时截图不要画鼠标。
- 理由（与之前"不画跟随光标"的拍板逻辑一致）：冻结模式下鼠标仍可移动，截图上那个静止光标会变成"假光标"（真实光标早已挪走），比不画更误导。
- **实现**：`CaptureShot()` 中 `const bool drawCursor = (g_cfg.lockMode == kLockMouse);` —— 锁鼠标模式下光标被钉在原地、位置真实恒定，**仍补画**；冻结模式下**不画**。新增日志 `shot WxH @(x,y) cursorDrawn=%d lockMode=%d`。
- **像素级验证**（把光标固定在屏幕中央 960,540，两种模式各截一张，用 System.Drawing 比像素）：
  - 光标区域 (940,520) 60×60：**365 个像素不同** → 一张画了箭头一张没画
  - 对照区域 (200,200) 60×60：**0 个像素不同** → 背景完全一致，差异确实来自光标
  - 日志佐证：`cursorDrawn=1 lockMode=0` / `cursorDrawn=0 lockMode=1`
- 保存的 PNG 用同一张位图，因此落盘截图同样遵循该规则。
- 收尾：测试产生的 PNG 已删除，`SaveShot` 关回 0，配置恢复 LockMode=1 / LockOnStart=0 / Debug=1，进程已清空。
